# NotifyX Git 工作流程

按以下顺序执行，每步确认成功后再进入下一步。全程遵守 `AGENTS.md` 与 `.skills/skills-git-commit-standard/SKILL.md`。

## 0. 环境约束（Windows PowerShell）

- 不支持 heredoc（`cat <<'EOF'`）：提交信息一律用多个 `-m` 参数拼接。
- 不支持 `&&`：顺序命令用 `;` 分隔。
- 批量替换文本用 `Get-ChildItem -Recurse -Filter pom.xml | ForEach-Object { (Get-Content $_.FullName -Raw) -replace '旧', '新' | Set-Content $_.FullName -NoNewline }`。

## 1. 前置检查

1. `git status` 确认变更范围；`git branch --show-current` 确认当前分支。
2. `git branch --no-merged master` 检查未合并分支；输出为空则无需合并。
3. 推送代码前必须跑与改动范围匹配的验证；架构、门禁、依赖、公共 API 变更必须全量 `mvn -B -ntp clean verify`。测试未通过不得提交推送。

## 2. 原子提交

按逻辑边界拆分提交，不要把实现、测试、文档、配置混在一个提交里。典型拆分顺序：

1. `feat/fix(<scope>)` — 实现代码（core、autoconfigure 等按模块分开）
2. `test(<scope>)` — 测试代码
3. `docs` — README.md、docs/design.md
4. `chore` — sample 配置、.memory（STATE.md、iterations/）

提交信息格式：`<Gitmoji> <type>(<scope>): <标题> (iter-NN)`，正文用 `- ` 列表写具体变更点（类名/方法名 + 动作）。

- Gitmoji 映射：✨ `:sparkles:` feat、🐛 `:bug:` fix、✅ `:white_check_mark:` test、📝 `:memo:` docs、🔧 `:wrench:` chore、♻️ `:recycle:` refactor。
- 零署名：禁止 `Powered by` / `Co-authored-by` / `Generated by` 等任何工具署名。
- 保持原子提交，一个提交只做一件事。

## 3. 推送 feature 分支

`git push -u origin <branch>`。推送后报告远程返回的 PR 创建链接。

## 4. 合并回 master

1. `git checkout master; git pull origin master`。
2. `git merge --no-ff <branch>`，合并信息格式：`:memo: merge: [iter-NN] <标题>`，与 `.memory/iterations/` 文件一一对应。
3. 合并后再次 `mvn -B -ntp clean verify` 确认全绿。
4. `git push origin master`。
5. 禁止重写 master 历史、禁止 force push master。

## 5. 版本号升级

1. 用户明确给出目标版本号后才执行；未获授权不得自行改版本号。
2. 全仓库 pom.xml 版本必须统一（父 pom + 全部子模块，当前 17 个文件）：用第 0 节的批量替换命令，将 `<version>旧版本</version>` 全部替换为新版本。
3. `git diff --stat` 核对变更文件数与模块数一致。
4. 单独一个 chore 提交：`:wrench: chore: 版本号升级至 <新版本>`，正文列出模块数量与包含的迭代。
5. `git push origin master`。

## 6. 禁止事项

- 未经授权不执行 `mvn deploy`、不发布 Central、不打正式 tag。
- 不跳过 hooks（`--no-verify`）、不绕过签名。
- 不提交构建产物、日志、IDE 配置、本地缓存与任何真实凭据。
- 发现 pom.xml 中有 `<version>` 被替换影响了非项目版本（如依赖版本）时，立即 `git diff` 逐文件核对并修正。
